4. Training & Inference — Learning vs Using a Model

Training adjusts model parameters from examples. Inference uses the learned parameters to produce outputs for new inputs. The two phases have different computational and operational requirements.

1. Training loop

  1. Prepare examples and labels or next-token targets.
  2. Run a forward pass to calculate predictions.
  3. Calculate a loss measuring prediction error.
  4. Backpropagate gradients through the computation graph.
  5. Use an optimizer to update parameters.
  6. Repeat over batches and monitor validation performance.
# Conceptual PyTorch-style training step
optimizer.zero_grad()
logits = model(inputs)
loss = loss_fn(logits, targets)
loss.backward()
optimizer.step()

2. Inference and decoding

Inference usually does not update weights. For autoregressive text generation, the model repeatedly predicts a distribution for the next token, selects a token, appends it to the context, and continues. KV caching reuses previous attention key/value computations.

3. Fine-tuning and prompting

ApproachWhat changes?Best suited for
PromptingInput context onlyFast iteration, instructions, examples
RAGExternal evidence supplied at runtimeFresh or private knowledge
Fine-tuningSome or all model parameters, or adapter parametersConsistent task behavior, style, specialized patterns

4. Compute and serving

Training is dominated by repeated forward/backward passes and optimizer state. Inference cost depends on model size, prompt length, generated token count, batching, hardware, and cache behavior. Quantization can reduce memory and increase throughput, with potential quality trade-offs.

5. Monitoring

Track latency percentiles, throughput, error rate, token counts, cost per request, timeouts, and quality regressions. Keep offline evaluation sets and compare model or prompt changes before production rollout.
