ConfigMaps, Secrets, and environment configuration

Separate application configuration from container images while controlling how sensitive values are stored and exposed.

1. ConfigMap for non-sensitive configuration

apiVersion: v1
kind: ConfigMap
metadata:
  name: web-config
data:
  LOG_LEVEL: info
  APP_MODE: production

Consume keys as environment variables or mount the ConfigMap as files. A process generally needs to reload or restart to pick up changed environment variables.

2. Secret for sensitive values

apiVersion: v1
kind: Secret
metadata:
  name: database-credentials
type: Opaque
stringData:
  username: app
  password: replace-with-a-managed-secret

Important: Kubernetes Secret data is base64-encoded, not automatically encrypted by that encoding. Enable encryption at rest, restrict RBAC access, avoid committing real credentials to Git, and consider an external secret manager.

3. Mount configuration

spec:
  containers:
    - name: app
      image: example/app:1.0
      envFrom:
        - configMapRef:
            name: web-config
      volumeMounts:
        - name: tls
          mountPath: /var/run/tls
          readOnly: true
  volumes:
    - name: tls
      secret:
        secretName: app-tls

4. Operational considerations

  • Use separate configuration per environment; avoid baking environment-specific values into images.
  • Keep credentials out of command arguments, logs, and shell history.
  • Limit who can read Secrets; namespace boundaries alone are not a complete security boundary.
  • Plan a safe rotation path and confirm the application reloads updated values.
