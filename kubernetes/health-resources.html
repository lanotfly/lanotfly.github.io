Health probes, requests, limits, and autoscaling

Tell Kubernetes when a container is alive, ready for traffic, or should be restarted—and reserve resources predictably.

1. Three probe types

  • Startup probe: gives a slow-starting application time to initialize before liveness/readiness checks take effect.
  • Liveness probe: detects a stuck process and can trigger a container restart.
  • Readiness probe: controls whether a Pod should receive Service traffic.
startupProbe:
  httpGet:
    path: /health/startup
    port: 8080
  failureThreshold: 30
  periodSeconds: 5
readinessProbe:
  httpGet:
    path: /health/ready
    port: 8080
  periodSeconds: 5
livenessProbe:
  httpGet:
    path: /health/live
    port: 8080
  periodSeconds: 10

2. Requests and limits

resources:
  requests:
    cpu: "250m"
    memory: "256Mi"
  limits:
    cpu: "1"
    memory: "512Mi"

Requests influence scheduling and are used by many autoscaling calculations. CPU limits can throttle a container; exceeding a memory limit commonly results in an OOM kill. Set values from observed load and performance tests rather than guessing.

3. Common failure signals
