Kubernetes security: RBAC, Pod hardening, and network controls

Reduce the blast radius by granting least privilege, restricting workload capabilities, and controlling communication.

1. Start with least privilege

Use Role and RoleBinding for namespace-scoped permissions where possible. ClusterRole and ClusterRoleBinding grant broader cluster-level permissions and should be used only when necessary.

apiVersion: rbac.authorization.k8s.io/v1
kind: Role
metadata:
  namespace: app
  name: pod-reader
rules:
  - apiGroups: [""]
    resources: ["pods"]
    verbs: ["get", "list", "watch"]
apiVersion: rbac.authorization.k8s.io/v1
kind: RoleBinding
metadata:
  name: app-pod-reader
  namespace: app
subjects:
  - kind: ServiceAccount
    name: app-reader
    namespace: app
roleRef:
  apiGroup: rbac.authorization.k8s.io
  kind: Role
  name: pod-reader

2. Harden the container

securityContext:
  runAsNonRoot: true
  runAsUser: 10001
  allowPrivilegeEscalation: false
  readOnlyRootFilesystem: true
  capabilities:
    drop: ["ALL"]

Apply a suitable Pod Security Standard, avoid privileged containers and host namespaces, pin trusted image versions or digests, scan images, and keep nodes and control-plane components patched.

3. Restrict network paths

Use NetworkPolicy to define which Pods may communicate. Policies require a CNI plugin that enforces them. Begin with an explicit threat model and test DNS, ingress, egress, and required service-to-service paths before enforcing a default-deny policy.

4. Protect secrets and identities

  • Do not treat base64 encoding as encryption.
  • Enable encryption at rest and restrict Secret read permissions.
  • Disable automatic ServiceAccount token mounting when a workload does not need Kubernetes API access.
  • Prefer short-lived workload identity and managed secret systems where available.
  • Audit access, separate duties, and test credential rotation.

5. Security review checklist

  • Who can create Pods, exec into containers, or read Secrets?
  • Can a workload escalate privileges or access host resources?
  • Are image sources, versions, and vulnerabilities controlled?
  • Are network flows intentionally allowed and observable?
  • Are audit logs, backups, patching, and incident response tested?
