Kubernetes troubleshooting workflow

Use a consistent path from symptom to evidence: workload state, events, logs, dependencies, and cluster capacity.

1. Start with the symptom

Identify the affected scope first: one container, one Pod, one Deployment, one node, one namespace, or the whole cluster. Record when it started and what changed recently.

2. A practical diagnostic sequence

kubectl get deploy,rs,pods -n app -o wide
kubectl describe pod <pod-name> -n app
kubectl logs <pod-name> -n app --all-containers
kubectl logs <pod-name> -n app --previous
kubectl get events -n app --sort-by=.lastTimestamp
kubectl get svc,endpointslices -n app

3. Match symptoms to likely causes

SymptomCheck first
PendingScheduling events, requests, taints, affinity, PVC binding
ImagePullBackOffImage name/tag, registry auth, network, pull policy
CrashLoopBackOffCurrent and previous logs, exit code, probes, config
Service unreachableSelectors, endpoints, ports, DNS, NetworkPolicy, app listener
Slow or throttledCPU/memory usage, requests/limits, saturation, downstream latency

4. Keep remediation safe

  • Prefer evidence collection before deleting Pods or changing configuration.
  • Compare desired state in Git with the live cluster; avoid unmanaged manual changes that drift from the source of truth.
  • For incidents, assess customer impact, mitigate safely, communicate status, and preserve evidence.
  • After recovery, write down the trigger, contributing factors, detection gap, and a preventive action.

5. SRE operational habits

Use service-level indicators and alerts, track rollout health, set realistic resource requests, test rollback paths, and practice restoring persistent data. A healthy Pod does not automatically mean the service is healthy end to end.
